# 扫描件 PDF 的 OCR —— 方案

## 一、现在是什么样

扫描件 PDF 里没有文字层，`pypdf` 抽出来是空的。界面已经会说了：

```
跳过的文件：扫描件.pdf —— PDF 中没有可提取的文字（可能是扫描件，需要 OCR）
```

也就是说，**提示已经在那里了，缺的是 OCR 本身**。文件在索引里搜不到，
Agent 读它也只会拿到那句「没有可提取的文字」。

## 二、实测数据（这台机器）

不是估算，是在这台 Cortex-A720（12 核）上真跑出来的：

| 项目 | 实测 |
|---|---|
| rapidocr 模型加载 | 0.39 秒 |
| OCR 一页 A4（1240×1754 中文） | **0.81 秒**（4 线程）/ 1.22 秒（2 线程） |
| OCR 每页耗的 CPU | 3.2 CPU-秒（= 吃满 4 个核） |
| 识别质量 | 6 行中文全部正确，无错字 |
| `pdfimages -j` 抽图 | 0.05 秒/文档（直接拿扫描件里的原图） |
| `pdftoppm -r 200 -gray` 渲染 | 0.28 秒/页 |
| 两条路线的识别结果 | **完全一致** |
| onnxruntime | 1.32.0 有 aarch64 cp311 轮子（23MB）✅ |
| rapidocr-onnxruntime | 1.4.4，15MB，模型打包在轮子里 ✅ |
| poppler | 系统已装（`pdftoppm`/`pdfimages`）✅ |

结论：一页约 **0.9 秒**（抽图路线），300 页的扫描书约 **4.5 分钟**。

## 三、流水线

```
扫描件 PDF
  └─ 抽文字层 → 空 → 判断「需要 OCR」
       └─ 入队（每页一格）
            ├─ pdfimages -j -f N -l N  → 那一页的图
            ├─ 抢大核池（写者）→ OCR → 放掉
            ├─ 页与页之间看「有人在说话」→ 有人就停
            └─ 文字写进缓存
                 └─ 索引器下一遍读到缓存 → 文件可搜、Agent 能读
```

**关键**：OCR 的结果必须缓存。否则每一遍扫描都要把整个书库重认一遍——
几小时一次，谁也用不了。

## 四、锁：要不要公用？（这是要商量的事）

### 现在大核池上都有谁

| 角色 | 身份 | 持有多久 |
|---|---|---|
| 模型（对话） | **读者** | 整个回答期间 |
| 以图搜图 | **写者** | 编码查询那一瞬 |
| 图片索引 | **写者** | **一张图一张图**（张与张之间放掉） |

文字索引（bge）**不在池子里**——它跑在小核上，模型不用那些核。

### 三个选项

**A. 完全不进池子**，OCR 自己跑、限制线程数

- 实测：4 线程的 OCR 吃满 4 个核，模型用 8 个线程 → 12 核的机器上直接抢。
- 后果就是代码里记着的那个数：有人跑重活时，对话从 27 tok/s 掉到 4 tok/s。
- **不行。** 池子存在的意义就是防这个。

**B. 进池子当写者，一页一页** ← **推荐**

- 每页独占 0.8 秒，页与页之间把池子放掉。
- 对话最多等一页（不到 1 秒）；池子空着的时候对话随时能插进来。
  （池子的规矩本来就是「模型优先」：写者在等的时候来读者，读者直接
  加进来排队，写者再等等。）
- 人在说话时（`interaction`）先停下不去抢 —— 这一条图片索引已经在做，
  OCR 照抄就行。
- 代价：以图搜图也是写者，OCR 持池的时候它可能被拒 → 那句
  「图片索引正在建」得改成通用说法（「机器正忙着」）。
- **每页放一次**是必须的：整本书一次的话，300 页要霸着池子 4 分半，
  对话 60 秒就超时了（「CPU 池在 60 秒内没有被释放」）。

**C. 自己一个小池 / 绑到小核**

- 这台机器的核不是干净的 4+8：2.6G×2、2.3G×2、2.2G×2、1.8G×4，
  「哪些是小核」并不干净，绑核靠不住。
- 就算绑了，小核上还有 bge 文本嵌入（`--threads 3`）在跑，OCR 一样抢它。
- **不如池子可靠**：池子是文件锁（flock），跨进程、跨重启都成立。

### 建议

**选 B**：OCR 进大核池当写者，一页一页；页与页之间让路给对话；
ONNX 线程数限制成 4（实测 0.81 秒/页，再多也不会更快，只是更抢）。

具体落法：

| 东西 | 怎么办 |
|---|---|
| 抢池子 | `get_big_pool().hold(timeout=…)`，**一页一次** |
| 让路 | 每页之间查 `interaction.is_busy()`，有人在说话就歇一会儿 |
| 线程数 | `RapidOCR(intra_op_num_threads=4)` |
| 工作时间 | 跟索引器一样受 `index_active_hours` 管 |
| 跑在哪 | **后端进程里的一个线程**（不是单独进程），理由见下 |

**为什么是线程不是单独进程**：

- OCR 要看「有人在说话」——那是进程内的状态，单独进程看不见；
- 模型 0.39 秒就加载完了，没有单独进程的必要；
- onnxruntime 推理时放开 GIL，后端不会卡；
- 跟图片索引是同一个样子（后端里一个线程），看门狗也能一起管。

## 五、OCR 的结果存在哪

放一张表，和别的库放一起：

```sql
-- .simplefilemanager/ocr.db
CREATE TABLE ocr_text (
    path       TEXT PRIMARY KEY,
    mtime      REAL,          -- 跟清单一样：文件改了就得重认
    size       INTEGER,
    pages      INTEGER,
    chars      INTEGER,
    text       TEXT,
    updated_at INTEGER
);
```

- 有效性靠 mtime + size 判断，跟索引清单一个规矩。
- 放数据库而不是散落的文件：备份脚本已经会带数据库，不用另外教它。
- 认出来的字是派生数据，删了重认一遍就行。

## 六、要写的组件

| 文件 | 干什么 |
|---|---|
| `backend/app/ocr.py` | OCR 引擎的封装：加载、认一页、抽图、渲染的兜底 |
| `backend/app/ocr_store.py` | 上面那张表：读缓存、写缓存、是否需要重认 |
| `backend/app/ocr_worker.py` | 后台线程：找需要 OCR 的文档、一页一页处理 |
| `backend/app/indexer.py` | `_read_content`：文档没文字时，先看 OCR 缓存 |
| `backend/app/routers/agent.py` | `tool_read_file`：扫描件也能读出文字 |
| `backend/app/routers/index*.py` | 索引页显示「识别中 / 识别完了」 |

改动很小：索引器只多一个「没文字就去缓存里找」的分支。

## 七、用户能看见什么

1. 索引页的「跳过的文件」里，扫描件从「需要 OCR」变成
   「正在识别（第 12/300 页）」，认完变成「已识别，300 页，8 万字」。
2. 认完之后，**文件能搜到了**（关键词 + 语义），Agent 也能读它。
3. 不给开关也可以——默认开着，但受「只在空闲时干」和「有人说话就停」
   管着，跟图片索引一个待遇。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 认一整本书要几分钟 | 一页一页、页与页之间放掉池子；有人说话就停 |
| 扫描质量差，认出一堆错字 | 一页认出不到 20 个字就当「认不出来」，不写进索引（宁可没有，不要脏数据） |
| 依赖变重 | onnxruntime 64MB + rapidocr 16MB，模型打包在轮子里；poppler 系统已有 |
| 认过的文件又改了 | 缓存按 mtime+size 判定，改了就重认 |
| 同一份文件重复认 | 缓存按路径存，一份只认一次 |

## 九、实施步骤

1. 依赖进 `requirements.txt`（onnxruntime、rapidocr-onnxruntime），
   锁版本，跑一遍后端测试确认没影响别的。
2. `ocr.py`：引擎封装 + 抽图/渲染两条路线 + 「认一页」。
   —— 这一步就能用命令行手动认一页，验证效果。
3. `ocr_store.py`：那张表。
4. `ocr_worker.py`：找文件、一页一页、抢池子、让路、写缓存。
5. 索引器接缓存 + Agent 读扫描件 + 索引页显示进度。
6. 测试：
   - OCR 引擎用假的（返回固定文字）→ 流水线各环节都能测，快；
   - 另加一个真的端到端测试（生成一个扫描件 PDF，跑完整条路），
     标成 slow。
